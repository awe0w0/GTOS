# IA32 通用文件存储后端

这是 Chromium/V8 原生文件接口的内核前置模块。当前 `FileStore` 已在真实 ATA PIO 上验证文件和目录读写、持久化及句柄回收；[原生文件 ABI](../../apps/native_files/README.md)另行验收了真实 CPL3 调用、用户页检查和退出回收；LLVM stdio、libc++ fstream 与完整浏览器仍待接入。

## 来源和构建

完整引入 [littlefs v2.11.3](https://github.com/littlefs-project/littlefs/releases/tag/v2.11.3)，固定提交 `6cb4e86540eca0d9ba62500a298385c9d863c8be`。`lfs.c`、`lfs_util.c`、`lfs.h`、`lfs_util.h` 与上游逐字一致，[BSD-3-Clause 许可](LICENSE.md)原样保留。

正常 Makefile 将上游 C99 源码和 C++ 适配编入 IA32 内核。所有内核对象继续使用 `tools/kernel-cxxflags` 中的整数策略；文件系统没有指令审计豁免。`LFS_NO_MALLOC` 配合真实静态缓存，`LFS_NO_INTRINSICS` 使用上游提供的纯整数位操作实现。未启用 `LFS_READONLY` 或 `LFS_NO_ASSERT`，完整读写算法和断言保留。

接口在 `include/storage/filestore.h`，实现和私有整数 C 辅助函数在 `src/storage/`。私有 C 头文件只服务于内核端 LittleFS，不是 Chromium 用户程序的通用 C SDK。

## 调用约束

设备必须先完成 Identify，且其容量和寿命在挂载期间保持稳定。挂载者独占指定卷；同一卷不能同时交给其他 `FileStore` 或应用包存储。

卷以 512 字节扇区传输，4096 字节逻辑块和 512 字节缓存工作；起点、长度均须按 8 扇区对齐，至少包含两个逻辑块。校验使用先比较、后减法的方式，拒绝扇区范围溢出。块回调继续检查块号、偏移、长度、传输对齐和空指针。

`Mount` 不格式化空白或损坏介质。`Format` 是明确的破坏性内核操作，只能由受信任的调用者对明确允许的新卷调用；已有挂载会拒绝格式化。当前桌面启动路径不调用它，也未接入新文件卷。测试只操作新建的独立磁盘，不触及现有应用和设置镜像。

对象、调用缓冲及路径都是受信任的内核数据。路径包括末尾 NUL 最多 512 字节，组件名保留上游的 255 字节上限，UTF-8 字节原样传入。文件上限保留上游的有符号 32 位范围；Seek 接受 64 位偏移并在运算前拒绝越界。返回负的 LittleFS/对应错误码，成功打开返回正句柄。

文件和目录共用 64 个静态槽位，每个文件有自己的 512 字节缓存和独立偏移。所有者须非零，只有相同所有者可以操作已打开的句柄；此规则不提供文件路径 ACL。句柄单调递增，在关闭、槽位复用和同对象重新挂载时不重置；超过有符号 32 位范围后明确失败。

`Close` 返回真实同步错误，但无论关闭是否失败都会使句柄失效。`Reclaim(owner)` 对该所有者的每个文件和目录执行真实关闭，继续回收所有槽位并报告第一个错误；其他所有者的句柄保留。失败关闭不保证数据已持久化。调用者须先关闭或回收句柄再卸载，并在对象销毁前卸载；原生文件服务在延迟 Reap 调用此接口，正常桌面尚未挂载文件服务。

文件、目录和挂载操作在 BSP 的中断保护范围内执行，同步 ATA 轮询的等待仍有上限；它不是 SMP 锁。原生服务已限制每次用户传输、检查整段用户页并快照输入，在延迟 Reap 关闭；不能直接把用户指针交给本接口。

## 实际验证

`tools/build-filestore-probe.py` 从真实源码构建 O0/O2 的完整后端、静态库及 ELF32 测试内核；测试内核不裁剪函数，所有 LittleFS/适配函数都经过整数指令审计。组件和测试内核均无未定义符号。

最终源码完成 174 次 ATA 客机冷启动：4 次常规写入/读取，2 次完整替换，以及两个优化级别各 42 个扇区边界的中断/恢复共 168 次。常规用例覆盖跨块读写、独立偏移、追加、文件空洞及截断零填充、UTF-8 文件、目录遍历/重命名/删除、255/256 字节组件名、满盘和释放后的空间复用、64 槽耗尽、所有者拒绝、陈旧句柄、同对象重新挂载、只读挂载、读写/Flush 失败及回收。卷前后各 8 个哨兵扇区保持不变。

独立 Linux 主机工具使用未修改的上游 LittleFS 和主机文件 I/O 读取 GTOS 写出的磁盘，并写入文件供 GTOS 冷启动读取。这只是磁盘格式交叉验证，不是 Linux Chromium/V8 参考运行的重跑，也不是 GTOS 用户态文件服务验收。

每个完整替换需要 42 次扇区写入。在第 1–41 次写入完成后停止，恢复读取完整旧文件；第 42 次完成后恢复读取完整新文件。GTOS 与上游读取结果一致。该模型验证已完成扇区之间的中断恢复，不证明物理磁盘的扇区原子性或真实断电行为。

测试栈固定为 16 KiB，底部哨兵未变化，ATA 回调处观测的常规最大栈深分别为 O0 1996 字节、O2 1408 字节；这是已执行路径的观测，不是所有文件系统调用路径的静态栈证明。原有原生用户栈、堆、进程容量及 FP 规则没有调整。

## 复现

需要 Python 3、GNU g++/binutils、主机 C 编译器、GRUB、xorriso 和 QEMU i386。每次输出使用不存在的新目录，所有日志和磁盘均保留：

```sh
python3 tools/build-filestore-probe.py /absolute/new-output --cxx /path/to/g++ --cc /path/to/gcc
```

`source-lock.json` 固定源码、已执行对象和测试内核。使用相同编译器/工具链，可以仅重建并逐字核对已执行对象：

```sh
python3 tools/build-filestore-probe.py /absolute/new-reproduction --cxx /path/to/qualified/g++ --build-only
```

提交前还逐个对照固定提交的 Git blob 恢复原始 LF 字节，并用限定到五个上游文件的 Git 属性保留原有格式。此前 Windows 检出副本的 CRLF 和原始执行记录均保留；恢复后 14 个对象与两个已执行测试内核逐字相同。

只构建模式不启动客机，也不会报告本次客机验收成功。验收汇总见 [acceptance.json](acceptance.json)。

有界原生文件 ABI、用户页检查和退出回收已独立验收。新增所有者句柄信息查询后，本后端完整重新执行 174 次冷启动与 84 个扇区中断边界，来源锁记录新的对象和内核。下一步实现 LLVM 文件提供者及 libc++ 文件流。完整 V8 Isolate、32 位 Chromium 网页浏览、视频播放与 HTML5 仍未在 GTOS 运行。
