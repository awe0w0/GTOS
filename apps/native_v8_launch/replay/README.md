# 真实 V8 负载运行的重放入口

本目录把"当前源码构建诊断内核 + 用固定镜像在其上真实运行 V8 负载"固定成可重放的脚本，不含任何预置产物。三个文件各管一件事：

- `kernel.py` —— 从**当前源码**编译 21 个目标（15 个运行库单元 + 观测器 + 4 个汇编入口），用 `llvm-nm` 从固定镜像读出 5 个状态符号写成 `entry-symbols.h`（内核与它要驱动的镜像绑在同一份字节上），按本树自己的诊断配方链接，并跑本树的指令审计。
- `guest.py` —— 把内核与镜像交给 QEMU 起动（`-kernel`/`-initrd`，镜像作为唯一 module），只认客人自己报的生命周期记录：`stage=4 result=0 exit=0 vector=0 fault=0`、`mask=0x7f`、`gc>0`、`Reap` 空闲页回到基线，以及 `GTOS REAL V8 LARGE HEAP RUN PASS`；退出码 33 才算通过，0、超时或日志缺记录都不算。
- `replay.sh` —— 环境驱动地把两者串起来（`GTOS_*` 变量见脚本头部），逐个配置运行并汇总。

## 实测记录（2026-10-30）

| 配置 | QEMU 退出 | 生命周期 | 结果 |
|------|-----------|----------|------|
| 32M / smp4 | 33 | stage4 result0 exit0 fault0，calls 6159，mask 0x7f，gc 2，Reap 空闲页 == 基线 | PASS |
| 64M / smp1 | 33 | 同上（64M 基线 12597 页） | PASS |

两配置各重复一次（`b1-v8-154-13`、`-14`），`b2-v8-154-02` 用本目录脚本从当前源码重建内核后再次两配置全过。历史 62 号镜像的 `calls 6159`、`mask 0x7f`、`gc 2` 与本次逐项一致；`Reap` 基线页数随当前内存管理代码变化（4427/12611 → 3135/12597），但"回到基线"这一条始终成立。

## 边界

- 只跑 jitless、单用户线程的负载；不含 Wasm、ICU、沙箱，也没有多线程 GC。
- 通过的是**这个负载在这个内核上**的生命周期，不是浏览器可运行、不是四作业 CI 复跑、不是远端验证。
- 工具与镜像从环境给出，脚本不写死宿主路径；镜像与工具的哈希都在每次运行的 `status.json` 里。
