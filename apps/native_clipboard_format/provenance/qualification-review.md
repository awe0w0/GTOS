## 来源检查中排除的错误结论

- `link-01` 在 LLD 前停于旧 heap 聚合回执中的公开 payload 清单哈希变化。
  该清单不属于 heap/exit 的真实 M/MD 消费闭包。没有把旧哈希替换成当前哈希；
  另行补验两个原对象的实际源依赖，聚合回执只保留为锁定的历史数据。
  其他原始 provider pool、格式与 fixture 的完整输入绑定保持。
- `provider-source-01` 在 heap M 后停于错误的全局成功条件。旧 exit03 是部分回执，
  所选 exit 单元的四项命令成功；后续 exit05 才有完整成功及缓存重新资格证据。
  新检查同时锁两份记录，不把部分回执写成整体成功。
- `provider-source-02` 在 heap M 后停于旧叶链接记录缺失。旧构建器的 File 目录实体化
  会为继承头文件创建链接，但回执只锁了最终文件与内容，没有锁叶节点的 readlink 文本。
  后续尝试只观察三个固定 File 源键，分别锁 gn-flush 叶路径、prepare04 唯一端点、
  双旧回执与生产器记录的 SHA，以及浅副本内容。已有链接仍匹配历史文本，其他
  未知节点拒绝；这些未完成尝试不作为最终来源资格。
- `provider-source-03` 在任何 Clang 调用前停于路径规范化重复。两份已锁 M/MD 各有
  113 个不同的原始条目；FILE.h 的第 71/72 项、wint_t.h 的第 89/93 项是两种路径
  写法，规范化后共 111 个唯一键。新检查仍逐条核对全部来源，另外比较完整的有序
  键/SHA 序列、多重集、次数和唯一映射，并精确固定两组重复的原拼写、位置与 SHA。

- `provider-source-04` 又在任何 Clang 调用前拒绝后段未记录的叶链接。没有继续
  扩大链接白名单。转而核对旧编译器驱动已经创建的实体源码副本：原驱动先绑定
  每份实际输入的 SHA，再逐文件 copyfile，原成功 CXX 的 cwd/source 正是该浅副本。

最终采用 heap 与 exit 各一次独立完整 M，两个原对象不重新编译。旧 heap depfile
哈希只作为本轮观察，新 M 与旧 MD 的实际 75 项来源交叉核对。exit 的历史 M/MD
文本本身有锁，113 原始条目和 111 唯一来源分别记录；本轮实际只读旧 CXX 所用的
实体浅副本及固定 Clang 资源头，检查文件与全部祖先的类型和双旧内容哈希。
新 exit M 必须与锁定的旧 postMD 逐条相等，含顺序、内容、次数及两个路径别名。
旧 pre-M 深层源视图不再是本轮输入；没有读取、准入或声称其未知链接保持不变。
Clang 的 bin、heap 与 exit 的两个实际工作目录另外逐级检查，避免先规范化 `..`
而漏过实际查找节点。终验再次核对登记节点的类型和 device/inode，以及已绑定文件内容。

负例的窄静态调用链另经复核：原格式 CHECK 引用真实 `CheckNoreturnError`，
链接选择旧 `libbase.check.o`（SHA256 `d5415d0b508dbba779b28198f6572a739608e7425a572fafd7b773a1a67bfcfc`）；
其析构调用 `ImmediateCrash`，非 OFFICIAL_BUILD、非 Windows 的实际分支调用 abort。
旧 CHECK 编译回执有四项未绑定 MD 输入；它们后来在 PMA 消费者的完整 1104 项闭包中
得到来源资格，但没有找到同一旧 CHECK 单元的后续完整 M/MD 回执。因此此处仅说明
这条静态调用链及本次选择的对象，不追认整个旧 CHECK 单元或所有旧 provider 的完整
编译来源资格。原生负例必须另行验证实际行为与精确退出值。

两个实际新 LLD 链接已经完整终验：各 2249 映像页、原有总容量 3401、两个构造函数、
21 个实际消费的格式 ABI 成员、零强未定义符号；没有增加既有可信启动配额。
